## 0. 这份文档是什么

本文件是 RM_Vision_2027 的**长期有效强制规范**，规定代码注释的写法。它不描述"最好怎么写"，只描述"本项目必须怎么写"。

| 项目 | 内容 |
| --- | --- |
| 适用范围 | `src/`、`tasks/`、`io/`、`tools/`、`tests/`、`calibration/`、`sim/`、`configs/`、`cmake/`、根级 `CMakeLists.txt` |
| 强制对象 | 所有新增文件、所有新增函数、所有新增变量与配置项 |
| 存量代码 | 不要求一次性回补；但**一旦本次改动触及某函数/变量，就必须按本规范补齐该处注释** |
| 与现有风格的关系 | 与仓库现有中文 `//` 注释、`clang-format`（`ColumnLimit: 100`）一致，不引入 Doxygen 等额外工具链 |
| 生效方式 | 作为项目固定上下文持续加载，见第 9 节 |

> 判断标准只有一条：**读者不打开实现代码，能否仅凭注释正确使用这个文件、函数、变量、配置项。** 做不到就是不合格。

## 1. 四条硬性要求（速查）

| 编号 | 要求 | 落点 | 合格判据 |
| --- | --- | --- | --- |
| **R1** | 文件顶部注释块 | 每个代码文件最上方 | 不读代码就知道这个文件整体负责什么 |
| **R2** | 函数/方法注释块 | 每个函数、方法、关键 lambda 上方 | 不读实现就知道功能、怎么传参、返回什么 |
| **R3** | 变量声明行注释 | 每个变量声明处 | 不猜就知道作用、单位、来源、约束 |
| **R4** | 配置文件参数行注释 | 每个配置参数的声明处 | 不改代码就知道能不能动、动了会怎样 |

四条要求**互相独立、不得替代**：文件头注释不能代替函数注释，函数注释不能代替变量注释，代码里的常量注释不能代替 YAML 里的参数注释。

## 2. R1：文件顶部注释块

### 2.1 位置

注释块必须是文件中的**第一段注释**，且紧贴文件顶部：

| 语言/文件类型 | 位置 | 说明 |
| --- | --- | --- |
| C++ `.cpp` / `.cc` | 第 1 行起，在 `#include` 之前 | 不允许放到 include 之后 |
| C++ `.hpp` / `.h` | `#ifndef` / `#pragma once` 之后，`#include` 之前 | 保证头文件完整性检查通过 |
| Python `.py` | shebang 与 `# -*- coding -*-` 之后 | 使用 `"""docstring"""` |
| CMake `.txt` / `.cmake` | 文件第 1 行起 | `#` 注释 |
| YAML `.yaml` | 文件第 1 行起 | `#` 注释 |
| Shell `.sh` | shebang 之后 | `#` 注释 |

### 2.2 必填内容

1. **职责**：一句话说明这个文件解决什么问题（不是"包含若干函数"这种空话）。
2. **关键流程 / 数据流**：文件超过 150 行、含多线程、含状态机时必须写；讲清"数据从哪来、经过什么、到哪去"。
3. **依赖与边界**：输入来源（相机/串口/配置文件/上游模块）、输出去向、线程归属。
4. **使用注意**：存在非显然前提时必须写（如"必须在 tracker 之前调用"、"非线程安全"、"配置缺失时回退默认值"）。

### 2.3 C++ 头文件模板

```cpp
#ifndef TASKS__AUTO_AIM__TRACKER_HPP
#define TASKS__AUTO_AIM__TRACKER_HPP

/*
 * 目标跟踪器：把逐帧检测到的装甲板串成稳定目标，并对外提供预测位姿。
 *
 * 数据流：Detector 输出的 Armor 列表 → 本模块（IMM/EKF 滤波 + 丢失计数状态机）
 *         → AimPoint（yaw、pitch、distance）→ Aimer / Shooter。
 *
 * 线程模型：由自瞄主线程独占调用，非线程安全；状态机状态为 lost / tracking / temp_lost。
 *
 * 注意：IMM 参数从主 config 同目录的 IMM.yaml 读取，读不到时使用内置默认值，
 *       因此更改调参文件不需要重新编译，但需要重启程序。
 */
class Tracker
{
  // ...
};

#endif  // TASKS__AUTO_AIM__TRACKER_HPP
```

### 2.4 C++ 源文件模板

```cpp

 *

 *       Aimer/Shooter（决策）、io::Serial（下位机通信）。
 */
#include "mt_standard.hpp"

#include <chrono>
// ...
```

### 2.5 Python / CMake 模板

```python
#!/usr/bin/env python3
# -*- coding: utf-8 -*-
"""
线格式映射层：把共享内存里的样本还原成进程内姿态，把进程内指令打包成线格式。

用途：
  * 无硬件联调：主程序以普通串口方式打开 slave 端，无法分辨对面不是真硬件
  * 异常注入：丢包、延迟、跳变、CRC 错误、MCU 重启

边界：只模拟下位机 → 视觉方向的上行数据，不解析视觉下发的控制指令。

```

```cmake
# ---------- 平台抽象（架构差异唯一来源） ----------
# 职责：根据目标架构选择相机 SDK 与 OpenVINO 运行库路径，并向调用方暴露统一变量。
# 注意：所有 x86_64 / aarch64 差异必须收敛在本目录，其他 CMakeLists 不得再判断架构。
```

### 2.6 禁止事项

- 写"本文件实现了一些工具函数"这类无信息量的描述。
- 写作者、日期、版本号（`git log` 已有，且必然过期）。
- 从其他文件复制粘贴文件头（最典型的事故：`.cpp` 顶着别的模块的说明）。
- 文件职责已大幅变化却不更新文件头。

## 3. R2：函数 / 方法注释块

### 3.1 固定格式

统一使用中文标签块，**不使用** Doxygen 的 `@param` / `@return`，避免两种风格混用：

```cpp
// 功能：<一句话说明这个函数做什么>
// 输入：
//   <参数名>  <类型>  <含义>，<单位 / 取值范围 / 空值或默认值语义>
// 输出：<返回值含义>，<单位 / 范围>；<出错时返回什么>
// 备注：<副作用：修改成员、加锁、阻塞、IO、抛异常>；无则写"无"
```

硬性规则：

| 规则 | 说明 |
| --- | --- |
| 四行齐全 | `功能`、`输入`、`输出`、`备注` 必须全部出现；无参数写 `输入：无`，无返回值写 `输出：无` |
| 参数逐行 | `输入：` 下**每个参数一行**，名字与签名完全一致，顺序与签名一致 |
| 单位必标 | 涉及物理量必须写单位：`m`、`m/s`、`rad`、`degree`、`px`、`ms`、`s` |
| 范围必标 | 有取值约束必须写，如 `0 ~ 1`、`> 0`、`[0, pi]` |
| 错误语义必标 | 失败返回 `std::nullopt` / 空 `vector` / `-1` / 抛异常，必须写明 |
| 副作用必标 | 修改成员变量、访问硬件、加锁、sleep、写文件，必须写明 |
| 行宽 | 遵守 `ColumnLimit: 100`，超长时在标签下换行续写 |

### 3.2 注释写在哪：声明处 vs 定义处

这是本规范最容易出错的点，规定如下：

| 位置 | 必须写什么 |
| --- | --- |
| **`.hpp` 声明处** | **完整契约**：功能、输入、输出、备注。这是唯一权威说明 |
| **`.cpp` 定义处** | **实现要点**：算法选择、线程/锁、异常处理、性能取舍。**不得重复声明处的契约，也不得与之矛盾** |
| **匿名命名空间 / `static` 内部函数** | 没有声明处，必须在该定义上方写完整四行块 |
| **超过 15 行的 lambda** | 在 lambda 上方写 `功能` 与 `输入/输出`（可用简写），说明它在整体流程中的角色 |
| **简单 getter / setter（≤ 5 行、无副作用）** | 允许单行 `// 返回当前跟踪状态：lost / tracking / temp_lost`；一旦涉及单位、加锁、懒加载，仍须四行块 |

### 3.3 完整示例

头文件声明（权威契约）：

```cpp
// 功能：加载 IMM/EKF 调参配置，缺失的键回退到内置默认值
// 输入：
//   path  YAML 文件路径，不可为空；文件不存在时全部使用默认值
// 输出：TargetConfig 结构体；读取失败不抛异常，返回全默认配置并打印 warning
// 备注：不修改全局状态；调用方应在构造 Tracker 时一次性加载，避免每帧读盘
static TargetConfig load(const std::string & path);
```

源文件实现（只写实现要点）：

```cpp
TargetConfig TargetConfig::load(const std::string & path)
{
  // 全程用 if 存在性判断逐个键覆盖，保证"少写一个键"不会让整份配置失效；
  // 序列长度超出固定槽位时截断，不扩容，避免调参文件名与模型数量不一致时崩溃。
  TargetConfig cfg;
  // ...
}
```

带副作用的写入函数：

```cpp
// 功能：解算目标在云台坐标系下的瞄准点，并平滑 yaw/pitch 输出
// 输入：
//   armors   当前帧检测到的装甲板列表，可能为空
//   timestamp 本帧采集时间，steady_clock 时间点，用于计算 dt
// 输出：AimPoint，yaw/pitch 单位为 rad，distance 单位为 m；无有效目标时 valid=false
// 备注：会更新内部滤波器状态与丢失计数，非线程安全；单帧耗时需 < 5 ms
std::optional<AimPoint> aim(const std::vector<Armor> & armors, TimePoint timestamp);
```

### 3.4 反例

```cpp
// 反例 1：只有一句话，参数与返回值全靠猜
// 解算
std::optional<AimPoint> aim(const std::vector<Armor> & armors, TimePoint timestamp);

// 反例 2：注释与签名不符（改参数后没改注释）
// 输入：armors 全部装甲板
std::optional<AimPoint> aim(const std::vector<Armor> & armors, TimePoint timestamp);

// 反例 3：废话注释，等于没写
// 功能：aim 函数用于执行 aim
void aim();
```

## 4. R3：变量声明行注释

### 4.1 必须加注释的变量

| 类别 | 例子 |
| --- | --- |
| 类成员变量 | `temp_lost_count_`、`last_timestamp_` |
| 全局 / 静态变量 | 单例、缓存、计数器 |
| 带物理单位的量 | 时间、角度、距离、速度、像素 |
| 有取值范围 / 会被夹取的量 | `r_clamp_min`、`mu_floor` |
| 来自配置、标定或通信协议的字段 | 从 YAML、串口帧、外参矩阵读出的值 |
| 涉及生命周期 / 所有权 / 线程归属 | 引用、裸指针、被其他线程写入的标志 |
| 魔数常量 | 用 `constexpr` 命名后仍需注释其来源与依据 |

**不必加注释**：循环下标 `i`/`j`、range-for 的迭代变量、函数内语义自明的临时量。前提是**命名本身已经表达了含义**；命名不合格应先改命名，而不是用注释补救。

### 4.2 格式

```cpp
// 作用；单位；来源；约束（按需保留，"作用"必填）
int temp_lost_count_ = 0;   // 连续丢失检测帧数；来源 max_temp_lost_count_；达到上限转入 lost
double bullet_speed_ = 28;  // 弹速，m/s；来自配置 bullet_speed；用于弹道补偿，范围 10 ~ 30
```

- 行尾注释与代码之间**至少两个空格**（`clang-format` 对齐后保持可读）。
- 私有成员保留仓库现有的 `_` 后缀，注释写业务含义，不写类型。
- 行尾注释总长度超过 100 列时，改为**变量上一行**的块注释。
- 坐标/向量类变量必须注明坐标系与分量顺序：

```cpp
Eigen::Vector3d t_camera2gimbal_;  // 相机光心在云台坐标系下的平移，m，分量顺序 [x, y, z]
Eigen::Matrix3d R_camera2gimbal_;  // 相机→云台的旋转矩阵，行主序，作用于 p_gimbal = R * p_camera
```

### 4.3 反例

```cpp
int count_;              // 计数 —— 什么计数？单位？上限？
double speed = 28;       // 速度 —— 谁的速度？m/s 还是 rpm？
bool flag = true;        // 标志位 —— 标志什么？谁改它？
```

## 5. R4：配置文件参数行注释

### 5.1 覆盖范围

`configs/*.yaml`、`cmake/*.cmake`、根级 `CMakeLists.txt` 中的项目自定义开关与目标、以及任何新增的 `.json`/`.toml` 配置。

### 5.2 每个参数必须写清四项

1. **作用**：控制什么行为，影响哪段代码。
2. **单位与类型**：`degree` / `rad` / `m` / `m/s` / `ms` / `px` / 布尔 / 枚举可选值。
3. **取值范围与默认值**：允许范围、超出会怎样、不写时用哪个值。
4. **调节影响**：调大 / 调小的后果，或开关打开后发生什么。

短参数用行尾注释；需要多行解释的参数用**紧贴参数上方的块注释**（与 `configs/IMM.yaml` 现行风格一致），二者不允许同时缺失。

```yaml
#####-----aimer参数-----#####
yaw_offset: 2                             # 云台 yaw 静态偏差补偿，degree；正值为向右补偿，范围 -10 ~ 10
pitch_offset: 6.5                         # 云台 pitch 静态偏差补偿，degree；实车标定得到，范围 -10 ~ 10
decision_speed: 7                         # 判定"目标高速旋转"的角速度阈值，rad/s；越小越容易触发提前量
auto_fire: true                           # 是否由自瞄程序接管射击；false 时只发云台指令，不下发开火

# 相机内参，行主序 3x3，来源：calibrate_intrinsics 输出；改相机或改分辨率后必须重新标定
camera_matrix: [1785.48, 0, 672.48, 0, 1785.02, 559.89, 0, 0, 1]
```

### 5.3 组织结构

- 用 `#####-----分组名-----#####` 划分参数组，与代码中的模块一一对应。
- 文件顶部写文件级注释块：这份配置给哪个可执行文件用、怎么启动、哪些参数必须按实车改。
- 成组参数（如 IMM 的三个模型）在组标题处说明"三项必须同时给"这类约束。

### 5.4 强制规则

| 规则 | 说明 |
| --- | --- |
| 无注释不新增 | 新增参数必须同时写注释，不允许"先能用，注释后补" |
| 键名一致 | 注释中的键名必须与代码读取处的键名完全一致（大小写、下划线） |
| 改值同步 | 修改数值必须同步修改注释中的默认值 / 范围描述，否则注释立即成为错误信息 |
| 单位显式 | 角度写 `degree` 或 `rad`，不写"角度"；距离写 `m`，时间写 `ms`/`s` |
| 注释不跨组 | 块注释与参数之间不允许空行，也不允许夹其他参数，避免注释错位到别的键 |

## 6. 书写风格与术语

| 项目 | 规定 |
| --- | --- |
| 语言 | 中文叙述，技术名词保留英文原词（PnP、IMM、EKF、YOLO、ROS 2） |
| 标点 | 中文句中使用中文标点，`,` 两侧不留空格；数字与单位之间留空格（`28 m/s`） |
| 行宽 | C++ 100 列（`.clang-format` 已固定），Markdown / YAML 建议 100 列内 |
| 缩进 | C++ 2 空格（Google 风格）；Python 4 空格 |
| 空话 | 禁止"这里""这个东西""处理一下"；必须写清对象与后果 |
| 死代码 | 直接删除；确需保留时写明原因，如 `// 3V3 无前哨站，该计数已停用` |
| 待办 | `// TODO(姓名或日期): 原因 + 预期动作`，禁止无主 TODO |
| 同步责任 | 改动行为必须在**同一次提交**中更新对应注释，评审时视为一处修改 |
| 注释掉的代码块 | 不允许长期保留；恢复靠版本管理，不靠注释 |

统一术语（避免同义词混用）：

| 概念 | 统一写法 | 不写 |
| --- | --- | --- |
| 装甲板 | 装甲板 / armor | 装甲片、板子 |
| 云台 | gimbal | 云台电机、PTZ |
| 位姿 | 位姿 / pose | 姿态（姿态专指 orientation） |
| 欧拉角 | yaw / pitch / roll | 偏航角、俯仰角混写 |
| 球坐标 | YPD（yaw, pitch, distance） | 极坐标 |
| 观测 / 状态 | measurement / state | 观测量、状态量混用 |
| 坐标变换 | `R_A2B`、`t_A2B` | `R_AB`、`T_AB` 含义不明写法 |

## 7. 提交前自检清单

| # | 检查项 | 结果 |
| --- | --- | --- |
| 1 | 新增文件是否有 R1 文件头注释块，且说明了职责、依赖、线程/边界 | ☐ |
| 2 | 新增/修改的每个函数是否有 R2 四行注释块，单位与错误返回是否写明 | ☐ |
| 3 | 契约是否写在 `.hpp` 声明处，`.cpp` 是否只写实现要点且无矛盾 | ☐ |
| 4 | 新增/修改的成员变量、全局量、魔数是否有 R3 行注释（含单位、来源、约束） | ☐ |
| 5 | 新增/修改的配置项是否有 R4 注释，且注释与代码键名、当前值一致 | ☐ |
| 6 | 是否存在与实现不符的过期注释 | ☐ |
| 7 | `clang-format` 是否已执行，无超长行 | ☐ |
| 8 | 是否残留无主 TODO 或注释掉的死代码 | ☐ |

**评审侧**：注释缺失属于阻塞性问题，与编译失败同级；不得以"改动小""以后补"为由合并。

## 8. 常见问题

| 问题 | 处理方式 |
| --- | --- |
| 一个函数参数很多（> 6 个），注释块太长 | 先考虑参数是否应该合并成结构体；确需保留时逐行列出，不允许"其余同上" |
| 模板函数 / 泛型代码 | `输入` 中写清概念约束（如"T 需支持 `operator+(T, T)`"），不要写具体类型 |
| 重载函数 | 每个重载都要写；若语义相同，`功能` 可相同，但 `输入/输出` 必须各自写清 |
| 接口实现（覆盖基类虚函数） | 定义处仍写完整块，注明覆盖的是哪个基类方法；或在基类声明处写契约并在此引用 `// 契约见 IXxx::foo` |
| 纯粹的数据结构体 | 文件头注释说明用途；每个字段写 R3 行注释；不需要 R2 |
| 单元测试文件 | 文件头说明测什么；每个测试函数上方一行说明"验证什么行为、对应哪个缺陷" |
| 读取配置的代码 | 在键名旁注明对应 YAML 键名，便于反查 |

## 9. 作为固定上下文持续加载

本规范不是"倡议文档"，而是**项目规则**。它只有在被每次开发会话实际加载时才有效，因此要求：

### 9.1 加载机制

| 机制 | 做法 | 作用 |
| --- | --- | --- |
| **A. 项目规则（首选，自动注入）** | 在 `.codebuddy/rules/coding-standards/RULE.mdc` 建一条 `alwaysApply: true` 的规则，正文声明"必须遵守 `docs/coding_standards.md`"并摘录四条要求；整个 `.codebuddy/rules` 纳入版本控制 | 每次会话开始时规则被加入模型上下文开头，助手在动手改代码前就已持有规范 |
| **B. 仓库入口文档引用** | 根目录 `README.md` 已链接本文件（"开发规范"与"参与开发"两处）；另可在根目录 `CODEBUDDY.md`（或 `AGENTS.md`，当无 `CODEBUDDY.md` 时会被自动加载）首段写明"编码前必须阅读 `docs/coding_standards.md`" | 新成员、外部工具与任何 AI 会话从仓库入口即可定位规范 |
| **C. 评审流程约束** | 第 7 节清单作为 MR/PR 模板与代码评审必查项 | 规范落到合并门槛，而不是只停在文档里 |

机制 A 的 `RULE.mdc` 建议内容（规则正文宜短，细节留在本文件，避免常驻上下文膨胀）：

```markdown
---
description: 代码注释强制规范（R1 文件头 / R2 函数 / R3 变量 / R4 配置）
alwaysApply: true
enabled: true
---

# 注释规范

编写或修改本仓库代码时，必须遵守 `docs/coding_standards.md`：

1. 每个代码文件顶部写注释块，说明该文件整体作用、数据流与线程/边界。
2. 每个函数/方法上方写注释块，含 `功能 / 输入 / 输出 / 备注` 四行，输入逐参数列出并标注单位。
3. 变量声明处写行注释，说明作用、单位、来源、约束。
4. 每个配置项写注释，说明作用、单位、取值范围与调节影响。

契约写在 `.hpp` 声明处；不得省略，不得留无主 TODO。
```

注意两点：

- 规则只在**会话开始时**加载，新建或修改规则后需**新开会话**才生效；当前会话不会热加载。
- 常驻（`alwaysApply: true`）规则建议控制在 3 ~ 5 条、单条 500 行以内；因此不要把整份规范复制进规则，用引用 + 摘要的形式。

### 9.2 对 AI 助手 / 自动化工具的行为约定

1. 生成新文件时**默认**包含 R1 文件头注释块，不询问是否需要。
2. 生成或修改函数时**默认**包含 R2 四行注释块，不因"保持代码简洁"而省略。
3. 新增变量、常量时**默认**写 R3 行注释，尤其标出单位、来源、约束。
4. 新增或修改配置项时**默认**写 R4 注释，并同步核对代码读取处的键名。
5. 改动重构时，只对**本次触及的函数与变量**补齐注释，不做无关的全文件重写。
6. 历史代码缺失注释时，以"随改随补"为原则，不强制一次性全仓库回填。
7. 若用户指令与本规范冲突（如明确要求不写注释），以用户指令为准，但需在回复中标注偏离了本规范。

### 9.3 维护规则

- 本规范只增不减；放宽任何一条要求都需要团队评审确认。
- 修改本文件须单独提交，提交说明写清"改了哪条、为什么"。
- 版本号与变更记录保持在第 10 节，便于追溯旧代码是按哪版规范写的。
